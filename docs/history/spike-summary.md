# AISEP 两个 spike 的合并总结

日期：2026-11-19
来源：
- `spike-linked-archi/spike-result.md`：由另一个会话执行。本会话重跑了它的复现命令：ArchiMate 3.2 和 4.0 的模型校验都没有问题（每次约 10 毫秒），12 个故意写错的负例模型全部被拦下。
- `spike-workbench-result.md`：本会话执行。

## 结论

两个 spike 都**有条件通过**，可以按计划推进。

## Linked.Archi（基础设施层底座）

- **许可证**：代码仓库是 Apache-2.0。实际用到的本体文件是 CC-BY-4.0，可以商用，只需署名。不要引入 `core-vis` 和 `edgy` 系列，它们是 CC-BY-SA，会把这条传染性条款带进我们的本体。本体源码仓库已不公开，245 个发布文件已按 SHA 锁定在 `vendor/`。
- **校验**：上游本体是“开放世界”的，拼错类型、悬空引用这类 AI 最常犯的错它不报。AISEP 必须补自己的闭世界规则，并关掉 RDFS 推理，原型已经做好。
- **性能**：用 pyshacl 做全量校验很慢，1000 个元素要 24–74 秒。改成直接查上游发布的关系表后是毫秒级，两者对比 2600 条随机关系，判定 0 处不一致。
- **AI 读写**：5 个 agent 做了 7 个任务，0 次用错类型，建模每次第一遍就通过校验，也会自己写 SPARQL 查询。
- **ArchiMate 4.0**：补测通过；把 3.2 的类型误用到 4.0 模型里，只有 AISEP 的规则能抓到。
- **没验证的**：跨记法追溯（BPMN → DDD → UML → 测试）。

## Orchestrator.inc（工作台骨架）

- **许可证与活跃度**：Apache-2.0，近 30 天 922 次提交。
- **流程**：主代理会自动拆任务，每个 worker 有独立分支、独立 worktree，各开一个 PR。批准、驳回、追问“为什么这么改”都跑通了。
- **扩展方式**：插件加不了界面，只能 fork 改前端。实测加一个面板改 16 个前端文件，约 20 分钟，测试全过，能热重载。
- **差距**：关口页没有模型差异图；批准没有按钮，也没有批准记录，要 AISEP 自建。

## 两边共同的启示（建议）

1. **AISEP 自己要补的三样东西**：闭世界校验规则、批准记录实体、影响分析口径。影响分析要说清沿哪些关系、往哪个方向、追几跳；现在每个 AI 各自定，同一问题得出 6 个和 7 个元素两种答案。
2. **一期 MCP Server 是两边的接缝**：它用毫秒级的查表校验加 SPARQL 对外服务，工作台 fork 后的前端可以直接调本机端口取数据画模型差异图。
3. **门禁可以写成 Claude Code hook**：hook 对 Orchestrator 拉起的 worker 也生效，模型校验可以在保存时和关口时自动执行。
4. **两边上游都迭代很快，都要锁版本**：本体按 SHA 锁定，Orchestrator 锁 stable 版本 v0.15.3，升级当作显式动作。
5. **两份报告都标了 Intel 未测**：两次 spike 都是在 Apple Silicon 上跑的。

## 口头摘要（不超过 200 字，带回设计会话）

两个 spike 均有条件通过。Linked.Archi：许可证可商用（CC-BY，避开 SA 系列），4.0 已复验；12 个负例全拦，查表校验毫秒级，AI 建模零类型错误；但需 AISEP 自补闭世界规则、关推理、统一影响分析口径；跨记法追溯未验证。Orchestrator.inc：Apache-2.0，自动拆任务、批准驳回追问都跑通；插件不能加界面，只能 fork，加一个面板改 16 个前端文件约 20 分钟；缺模型差异图和批准记录，需自建。两者以一期 MCP Server 衔接，门禁可复用 Claude Code hook，均需锁版本。Intel 均未测。
