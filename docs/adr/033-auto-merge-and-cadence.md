## ADR-033 · 2026-11-27 · 自动合并与合并节奏

- **状态**：已采纳（Albert 2026-11-27 拍板，拍板记录第 23、26、27、30 条，经协调会话转达；第 30 条修订第 29 条：验证批 B′ 推迟，改做拆 `docs/decisions.md`，采纳批量合并设计提案 `coordination/design-batch-merge-20261127.md` r2 的 Q1–Q3）。修订下列条款的执行方式或适用范围，各自原文不改，以本条为准：ADR-026 决策第 5 条末句与其 2026-11-27 补记「合并规则」末句（新铸 IRI 合并前报 Albert 过目）；ADR-022 2026-11-27 补记的批末核对（与第 6 款的批末核对合为一次）。ADR-019 第 1 款的评审分级与第 2 款的冻结范围、ADR-020 第 1、2 款（自动合并、只由协调会话合并）、ADR-021、ADR-024、ADR-027 不变。本条不改合并判据（`mergecheck` 的检查项、三步合并、`--match-head-commit`、合并后核验都不变），按第 3 款经 agent 双路独立评审合入，按 ADR-021 第 2 款不做跨模型评审。
- **背景**：今天的实测（`coordination/speedup-plan-20261127.md` 第 1 节）里，慢的大头不是 CI（必需检查全绿中位 8.9 分钟），而是 PR 就绪后没人合（就绪到合并中位约 250 分钟，隔夜 503–631 分钟），其次是更新分支、重评与串行等待。第二批 9 次「把 main 合进 PR 分支」里 5 次有文本冲突，其中 4 次在 `docs/decisions.md`（设计提案第 1 节）。Albert 原话：「自动批量做，不用我审核，改 ADR」（第 26 条）。
- **决策**：
  1. **就绪的定义。** 一个 PR 同时满足下面各条，就是「就绪」：
     - ① CI 的全部必需检查在 PR 头 H 上通过（当前为 `gate`、`mergecheck`、`pytest`，以分支保护设置为准）；
     - ② 评审条件在 H 上满足：合并前评审类（ADR-019 第 1 款）要有 **agent 双路独立评审**（两个互相独立、都没参与该 PR 实现与测试的 agent 评审人）在 H 上的结论，且都没有阻断问题；H 是评审过的头只因 `git merge origin/main` 解冲突、没改逻辑而产生的新头时，按拍板记录第 23 条②只需一个轻量复核在新头上无阻断；用豁免的，按原条款核对通过即可：批准提交豁免（ADR-019 第 3 款）、批准专用 PR 机械核对（ADR-021 第 1 款）；合并后评审类（ADR-019 第 1 款白名单、ADR-024 第 1 款、ADR-027 第 1 款）不需要合并前评审；
     - ③ 需要时，H 上 `negatives` 的核对通过（ADR-022 第 1 款、ADR-024 第 5 款）；
     - ④ 与当前 `origin/main` 无冲突：`git merge-tree --write-tree origin/main H` 没有冲突；
     - ⑤ 不是草稿 PR；
     - ⑥ Albert 没有在会话里说「先别合 #N」。
     「双路」是两路 agent 独立评审，不是跨模型评审；跨模型评审的范围与「先问 Albert」照旧按 ADR-021 第 2 款。
  2. **就绪即合，含定时巡检与夜间无人值守（第 26 条）。** 协调会话（ADR-020 第 2 款，仍是唯一执行合并的会话）发现 PR 就绪就合，不攒批、不等 Albert；合并方式照旧（`AGENTS.md`「分支与合并」第 2、3 条，需要时走三步）。另起一个周期巡检（Cron 或 Monitor，间隔以 15 分钟为参考），每次：对照「已评审的头」与必需检查结论，就绪未合的按第 5 款排序后合掉；新头没人评的派评审；一轮合并结束时做第 6 款的批末核对。夜间 Albert 不在场时照样执行，但遇到本该报告 Albert 的情形（合并后核验不通过、批末核对失败、`STOP-MOVED`、ADR-024 恢复条件出现等）只做规则写明的处置（开 revert PR、暂停同类合并、停止本轮合并），不做规则外的取舍，等他回来在汇总里报告。
  3. **新铸 IRI 与治理规则改动经 agent 双路评审即合，合并后汇总告知 Albert（第 27 条）。**
     - **范围**：PR 新铸的 IRI（含测试 IRI，即测试夹具、负例模型里新铸的 IRI，以及运行时按规范 §3 生成的批准记录、活动 IRI 的测试样例），以及治理规则改动：`AGENTS.md`（含硬规则）、`docs/decisions.md` 的 ADR（新增或补记）、合并规则（`AGENTS.md`「分支与合并」与写合并判据的文档）。这些 PR 按 ADR-019 第 1 款本来就走合并前评审，现在只要第 1 款②的 agent 双路独立评审无阻断、其余就绪条件满足，就由协调会话合并，**不再合并前交 Albert 过目或先请示**。
     - **合并后汇总**：协调会话在一轮合并结束后（夜间则在 Albert 回来后的第一次汇报里）汇总告知 Albert：PR 号、新铸 IRI 清单（含测试 IRI）、治理规则改动的要点、revert 与失败处置，以及按规则仍需他定的事项。新铸 IRI 合入后不能撤回，只能按硬规则 5 退役加新铸；这是本条接受的代价，靠双路评审与合并后汇总兜底。
     - **逐条点名修订的以往条款**（原文不改，按本条理解）：
       - ADR-026 决策第 5 条末句「新铸 IRI 合并前报 Albert 过目」：改为合并后汇总；
       - ADR-026 补记（2026-11-27，issue #160）「合并规则」末句「新铸 IRI 合并前报 Albert 过目（本 ADR 决策第 5 条）不变」：同上；
       - ADR-030 第 8 款「Albert 2026-11-27 已过目同意（ADR-026 第 5 款的做法）」与 `docs/specs/c4-archimate4-step4.md` 第 5 节标题「请 Albert 过目」：作为当时的记录保留，今后不再是必经做法；
       - 拍板记录第 4 条「新 IRI 报 Albert 过目」、第 20 条推迟项触发后「把新 IRI 交 Albert 过目」：改为合并后汇总；
       - `AGENTS.md`「分支与合并」第 2 条 `modules/ext-actions/**` 一条末句「新铸 IRI 合并前仍报 Albert 过目」：随本条改写；
       - 以往「治理规则改动（`AGENTS.md`、ADR、合并规则）先请示 Albert 再合」的做法：改为本款的双路评审即合、合并后汇总。
     - **不变的**：本条只改「合并前要不要 Albert 看」，不改「哪些事由 Albert 定」。以往条款写明由 Albert 定的事项照旧由他定，例如 ADR-024 恢复条件是否恢复、ADR-019 第 4 款与 ADR-022 第 2 款 `negatives` 是否升为必需检查、ADR-019 第 2 款冻结范围是否开例外、ADR-032 第 9 款的待定项、ADR-021 第 2 款每次跨模型评审前先问他；落实这些事项的 PR 要先有他的决定，有了之后按本款合并。`AGENTS.md`「工作方式」末条「已拍板的决策不再重新讨论；发现冲突先报告，不自行改动」不变。
  4. **唯一保留给 Albert 本人的是批准记录。** 模型里的批准记录（`aisep:ApprovalRecord`）只能由 Albert 本人做出，AI 不得以他的名义新增（`AGENTS.md`「分支与合并」第 2 条末段、ADR-024 第 7 款），这一条不变，也不因第 2、3 款的自动合并而放宽。
  5. **冲突感知排序（第 23 条①）。** 几个 PR 同时就绪时，协调会话先用 `git merge-tree --write-tree H_i H_j` 两两试合（再加各自与 `origin/main` 的试合，即第 1 款④），与谁都不冲突的先合；互相冲突的按依赖顺序合（被依赖的先合），后合的在前一个合入后 `git merge origin/main` 解冲突、按第 1 款②只派轻量复核；彼此不冲突、需要更新的几个 PR 可以并行更新、并行跑 CI、并行复核。合并本身仍串行，一次一个（接口文档 §5.9 R4-11 ①）。
  6. **有条件地不更新分支，与批末核对（设计提案 Q3）。**
     - **何时可以不更新**：main 在 H 的 CI 之后前进了、而 PR 与新 main 之间**既无文本冲突、也无语义依赖**时，才可以不把 main 合进 PR 分支、直接按现行规则合并（三步合并照旧对当前 T 重算 `mergecheck`）。语义依赖包括但不限于：两边改到同一个模块，或一边依赖另一边新增的模块、IRI、函数、文件或测试（例如模块升版规则：第二批 #173 两次干净更新后补升了 #161 改过的模块版本）；ADR 或其他编号依赖（第二批 #161 改号为 ADR-029）；一边改了另一边要过的检查、形状或测试；一边改了 `.github/workflows/**` 或负例清单。拿不准就更新。每次「不更新」在合并说明或日志里写明语义依赖的判定。
     - **批末核对，与 ADR-022 补记合为一次**：一轮合并（协调会话连续合并的若干 PR，即 ADR-022 补记所说的「一批」）结束时，最迟在下一轮开始前，协调会话一次做完：① ADR-022 补记要求的逐个核对这一轮每个负例清单类合并的 M 上 `negatives`；② 这一轮最后一个合并提交 M_k 上 push 触发的 `gate`、`pytest`、`negatives`，用 ADR-022 第 1 款的命令（`check_name` 依次换成 `gate`、`pytest`、`negatives`，H 换成 M_k），每个输出都必须恰好是 `["success"]`（还没跑完就等它跑完再判）。结论补记到这一轮各 PR 的评论。
     - **失败处置**：先对同一个提交重跑一次失败的 job，排除偶发失败；仍失败，按 M 逐个查 push 运行（每个 M 各有自己的 push 运行，`gate.yml` 的 push 运行按 sha 分组、不取消），找到第一个失败的 M_j，**只 revert 出问题的那个 PR**（不二分、不连串 revert），报告 Albert；`negatives` 失败的，另按 ADR-022 补记暂停后续负例清单类合并，直到修复合入、修复后的 main 头上 `negatives` 为 `success`。
     - 这一款不触及 ADR-019 第 2 款的冻结范围：只改更新分支的时机与合并后多看一次 push CI，`mergecheck` 判据与三步合并不变（设计提案第 5 节 S10）。
  7. **验证批 B′ 推迟（第 30 条）。** 验证批（几个就绪 PR 先在一棵叠合树上跑一次 CI，再逐个按现行规则合并，骨架取自 Kubernetes Tide）现在不做：按设计提案第 1 节的同批上限探针，第二批 8 个 PR 里能同批的最多 2 个，每批反而多 12–19 分钟；它还要改 §5.9 的设计前提，须对 ADR-019 第 2 款冻结范围开例外。**触发条件**（任一出现即重新提出）：一轮合并的批末核对因 PR 之间的语义冲突（而不是单个 PR 自身的问题）失败累计 ≥ 2 次；或者拆 `docs/decisions.md` 后能同批的 PR 经常 ≥ 3 个。届时连同冻结范围例外一起请 Albert 定，并先问是否要跨模型评审；设计备忘见设计提案第 6、8 节。同样推迟的还有：一个合并提交合进一批（破坏一 PR 一合并提交与 H 判据）、把仓库转到组织名下用 GitHub merge queue、B-ff 快进链，触发条件见设计提案第 12 节。
  8. **拆 `docs/decisions.md`（第 30 条、设计提案 Q2）另有 PR。** 把 `docs/decisions.md` 拆成一个 ADR 一个文件（参考 adr-tools、MADR），含编号分配办法、`AGENTS.md` 白名单排除项与 `decisions.md:行号` 引用的迁移，由单独的设计与 PR 处理；本条只引用，不在本条落实。
- **理由**：
  - 就绪即合与巡检直接对准实测的大头（就绪到合并的等待），合并判据本身不变，风险低。
  - 新铸 IRI 与治理规则改动此前在 agent 评审之外还要等 Albert，是夜间积压的主要原因之一；Albert 拍板把这一步改为合并后汇总，只把事后补不回、也无法由他人代做的批准记录留给他本人。
  - 不更新分支能省掉一次「合 main → 等 CI → 复核」，但也去掉了合并前唯一一次叠合树测试；所以只在既无文本冲突也无语义依赖时才不更新，并在批末多看一次最后一个 M 的 push CI 兜住漏网的叠合问题，成本几乎为零。
  - **参考对象与差别**（链接于 2026-11-27 核实可访问）：
    - Kubernetes Prow Tide（[文档](https://docs.prow.k8s.io/docs/components/core/tide/)）：PR 满足查询条件（标签、必需检查）就自动合并，不等人点按钮；批先在合成 ref 上测一次，通过后对每个 PR 各调一次合并接口并带上该 PR 的头 SHA。第 1、2 款的「就绪即合」借它；差别是 Tide 要求每个 PR 都在最新 base 上测过，本条不要求（分支保护不开「要求分支最新」），改用第 6 款的条件加批末核对兜底，三步合并类 PR 另有 `mergecheck` 对当前 T 重算；验证批推迟（第 7 款）。
    - Bors-NG（[仓库](https://github.com/bors-ng/bors-ng)，已于 2024 年归档；[文档](https://bors.tech/documentation/)）：评审人批准（`r+`）后由机器人合并，「main 永远是绿的」。借「批准后无人值守地合」；不照搬它「一批一个合并提交、main 快进」的做法，那会丢掉每个 PR 自己的合并提交与 H 判据。二分对同批 ≤ 2 个 PR 没有意义，第 6 款按 M 逐个定位，不二分。
    - Mergify（[合并队列](https://docs.mergify.com/merge-queue/)、[合并队列规则](https://docs.mergify.com/merge-queue/rules/)、[批处理](https://docs.mergify.com/merge-queue/batches/)）：入队条件（针对 PR 本身）与合并条件分开，条件满足就自动入队、自动合并。第 1 款把「就绪」写成一组可机械核对的条件借这种写法；不引入有写权限的第三方 App。
    - GitLab merge trains（[文档](https://docs.gitlab.com/ci/pipelines/merge_trains/)）与 GitHub merge queue（[文档](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)）：按顺序把每个改动叠在前面的改动上验证，失败的移出、其余重建。第 5 款的冲突感知排序与第 6 款「只 revert 出问题的 PR」借这一思路；差别是本条不在合并前建叠合树，而是合并后看最后一个 M 的 push CI，因为 GitHub merge queue 只对组织名下的仓库开放，本仓库属于个人账号（公开仓库，ADR-020 第 4 款）。
    - **与所有参考对象最大的不同**：它们用「队列或批的 CI 通过」替代逐个检查；AISEP 的批准判据依赖每个 PR 自己的 (T, H)，批 CI 不能替代，只能叠加，所以本条只改节奏与排序，不改判据。
- **后果**：
  - `AGENTS.md`「分支与合并」第 2 条补就绪即合与巡检、自动合并范围（新铸 IRI 与治理规则改动）、冲突感知排序、有条件不更新分支与批末核对的口径，`modules/ext-actions/**` 一条末句按第 3 款改写。`docs/mcp-interface.md` §5.9「不用合并队列」一句的平台事实更正为与现状一致（仓库属于个人账号、现为公开仓库；GitHub merge queue 只对组织名下的仓库开放）：只更正事实，§5.9 的规则不变。
  - **风险**：① 无人值守时只有 agent 把关，双路评审都漏看的问题要到合并后汇总或事后才被发现；新铸 IRI 合入后不能撤回（第 3 款）。② 语义依赖判定漏判时，叠合树问题在合并后才暴露：拿不准就更新，批末核对最后一个 M 的 push CI 兜底（第 6 款）。③ 坏提交在 main 上的暴露窗口按 ADR-022 补记拉长到一轮合并。④ 偶发失败让批末核对误报：先重跑一次再判。
  - **出口标准**：下一轮合并的日志里，每次「不更新」都写明了语义依赖的判定，批末核对的结论（每个负例清单类 M 的 `negatives`、最后一个 M 的 `gate`、`pytest`、`negatives`）记进 PR 评论；夜间巡检至少跑过一轮，合并后汇总按第 3 款的内容发给了 Albert。
